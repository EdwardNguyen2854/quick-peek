# Decision Log — Enterprise Release

> **Quick Peek v0.4** — Enterprise Release  
> **Date**: 2026-06-06  
> **Status**: All decisions implemented

---

## 1. Pure-Python LDAP over SAML/OIDC

**Status**: Implemented

**Context**: Quick Peek needed enterprise authentication — logging in with corporate Windows domain credentials. Three options were on the table: LDAP bind, SAML, and OIDC. The decision had to account for the PyInstaller frozen exe deployment model (no system DLLs allowed), the air-gapped LAN environment (no browser redirect flows), and the need for a break-glass local admin fallback.

**Decision**: Use **`ldap3` (pure Python)** for bind-only LDAP authentication. Keep local PBKDF2 as the break-glass admin fallback. No SAML, no OIDC.

**Rationale**:
- `ldap3` is pure Python (no system DLLs), which is critical for the PyInstaller frozen .exe — SAML/OIDC would require either system-level IdP agents or a heavy library like `python3-saml` that depends on `xmlsec1` system binaries.
- LDAP bind is a single round-trip to check credentials and read groups — well-suited to a LAN desktop tool with low latency to the domain controller.
- The codebase already uses PBKDF2 (`get_password_hash`, `verify_password` in `auth.py`), which serves as the local fallback when LDAP is unreachable.
- Groups-to-permissions mapping is configurable via a simple CSV env var (`QUICKPEEK_LDAP_GROUP_MAP`) — no admin UI changes needed for v0.4.

**Alternatives Considered**

| Alternative | Why Rejected |
|-------------|--------------|
| SAML (e.g., `python3-saml`) | Requires `xmlsec1` system binary — incompatible with PyInstaller frozen exe. Designed for web SSO with browser redirects. |
| OIDC (e.g., `authlib`) | Requires browser redirect flow to identity provider — doesn't fit an air-gapped desktop tool. Adds OAuth state management complexity. |
| Kerberos (SSPI/`sspi`) | Native Windows-only. Not cross-platform. Requires the client to be domain-joined. |
| Local-only auth (v0.3) | Rejected — the primary feature request for v0.4 was enterprise SSO integration. |

**Consequences**
- LDAP is bind-only: no SAML/OIDC support for organizations that don't use Active Directory. This closes the door on cloud IdPs (Okta, Azure AD SSO via SAML) for now.
- `ldap3` is added to `quick_peek.spec` `hiddenimports` for PyInstaller compatibility.
- The login page now has two visual modes (LDAP-first, local-fallback) adding UI complexity.
- A "Test LDAP Connection" button in Admin UI was required to reduce support tickets.

## 2. `X-API-Key` Header over OAuth Bearer for API Keys

**Status**: Implemented

**Context**: External tools (CI scripts, backup pipelines, automated QA) needed to access Quick Peek without interactive login. The existing auth system uses Bearer JWTs that expire after a configurable TTL. Long-lived credentials needed a transport mechanism that works with `curl`, Python `requests`, and PowerShell `Invoke-RestMethod` with minimal friction.

**Decision**: Use the **`X-API-Key` custom HTTP header** for API key authentication. Keys have a `qpk_` prefix for visual identification and are SHA-256 hashed for storage.

**Rationale**:
- `X-API-Key` is the simplest possible pattern for CI scripts: `-H "X-API-Key: qpk_..."` works with every HTTP client without special OAuth2 flows.
- SHA-256 hashing uses stdlib `hashlib` — no extra dependencies. PBKDF2 is unnecessary here because API keys are high-entropy random strings (32 bytes = 256 bits).
- The `qpk_` prefix makes API keys easily identifiable in logs, error messages, and the admin UI. The first 8 characters are stored plaintext for display.
- Keys are not typed by users — they're generated by the system and returned once, so human-factors like "looks like a password" don't apply.

**Alternatives Considered**

| Alternative | Why Rejected |
|-------------|--------------|
| OAuth2 Client Credentials flow | Requires token endpoint, client_id/secret rotation, bearer token refresh. Overkill for a LAN tool. |
| Bearer token with long TTL | JWTs are not revocable without a blocklist. Stateless verification is the whole point of JWTs — adding a blocklist negates the benefit. |
| Basic auth (`Authorization: Basic base64(api_key:)`) | Misuse of HTTP Basic auth semantics. Awkward in some HTTP libraries. |
| Query parameter (`?api_key=...`) | API keys in URLs are logged by proxies, stored in browser history, and leak via Referer headers. |
| Cookie-based | Not suitable for non-interactive clients (curl, scripts). |

**Consequences**
- API keys can be soft-revoked by setting `api_keys.revoked_at` — no need to remove the row, revocation is immediate.
- Keys are created by admins only (gated by `manage_users`). Self-service key creation is deferred to v0.5.
- The `current_user` dependency was modified to try JWT first, then API key header — a single dispatch function handles both.

## 3. M2M Tag Schema over JSON Column

**Status**: Implemented

**Context**: Files needed user-applied labels ("weldment", "for-review", "critical") with the ability to filter search results by tag. Two architectural approaches exist: a JSON array stored on the file row, or a proper many-to-many relationship with a tags table and a junction table.

**Decision**: Use a **proper M2M schema** with `tags` and `file_tags` tables. Add a separate `file_metadata` table for typed fixed fields (project code, revision, supplier, cost center) plus a `custom_json` escape hatch.

**Rationale**:
- Tags are genuinely many-to-many: a file can have multiple tags, a tag can apply to many files. A JSON column would make it impossible to efficiently query "all files tagged with `critical`" or "files that have ALL of these 3 tags".
- The `tags` table supports scoped tags (`shared` vs `user`), colored display (`color` hex), and the `file_tags` junction table tracks `applied_by` and `created_at` for audit.
- Foreign keys with `ON DELETE CASCADE` mean tag associations are automatically cleaned up when a file is removed during reindex — no orphaned tag references.
- Separate `file_metadata` table for structured fields avoids polluting the general-purpose tag system with domain-specific columns. The `custom_json` escape hatch covers any fields not in the fixed schema.

**Alternatives Considered**

| Alternative | Why Rejected |
|-------------|--------------|
| JSON array in `files.tags` column | Cannot index or JOIN efficiently. No referential integrity. Cannot query "all files tagged X" without a full table scan. |
| JSON column in `files` for everything | Mixes tags and metadata in one blob. Harder to validate, harder to migrate. |
| EAV (Entity-Attribute-Value) pattern | Flexible but complex queries. Every tag filter becomes a multi-JOIN nightmare. Overkill for simple tag filtering. |
| SQLite `json_each` with generated columns | Workable for small datasets but doesn't scale. Loses the ability to display tag colors and scope. |

**Consequences**
- Tags do NOT survive a file delete+reappear cycle (e.g., file deleted from disk, re-indexed, then recreated). When a file is removed and a new file appears at the same path, it gets a new `files.id` and the old tag associations are cascade-deleted. Acceptable for v0.4.
- `_file_payload()` in `peek.py` now runs additional queries to attach tags and metadata to every search result — minor performance cost.
- The `tag_audit_log` table provides an audit trail for tag add/remove actions.

## 4. Default-Allow Folder Scoping for v0.4

**Status**: Implemented

**Context**: Per-folder permission scoping was the most requested enterprise feature, but it introduces a fundamental change in access semantics. In v0.3, all indexed files are visible to all authenticated users. In v0.4, files can be restricted by folder path. The question was: when no scope matches a file, should access be granted (default-allow) or denied (default-deny)?

**Decision**: **Default-allow** for v0.4, controlled by `QUICKPEEK_FOLDER_DEFAULT_ALLOW=True`. v0.5 will flip the default to `False`.

**Rationale**:
- Default-allow means existing v0.3 deployments upgrade with zero configuration changes — no folder scopes exist, so every file matches the default and access continues to work.
- Format permission (`FORMAT_PERMISSION` in `peek.py`) still gates every search, so default-allow does not open a security hole — a user still cannot search STEP files without `view_step`.
- P0 security fixes to `raw_file` and `preview_file` are applied regardless of default-allow — these endpoints now always check folder scope + download permission.
- A startup warning log is emitted when default-allow is enabled, alerting admins that v0.5 will change the default.
- Administrators who want stricter control can set `QUICKPEEK_FOLDER_DEFAULT_ALLOW=False` and create explicit allow rules — the deny-first evaluation still works correctly.

**Alternatives Considered**

| Alternative | Why Rejected |
|-------------|--------------|
| Default-deny from v0.4 | Would break every existing v0.3 deployment: all files would become invisible until admins created allow rules for every folder. Unacceptable upgrade experience. |
| Default-deny with auto-create of allow rules | Too magical — auto-creating rules for every existing folder path would be complex and error-prone. |
| Per-user default (each user chooses) | Adds UI complexity, violates "admin controls security" principle. |
| No default — require explicit rule for every path | Impractical — thousands of paths would need rules. |

**Consequences**
- v0.5 will release with a migration guide that recommends setting `QUICKPEEK_FOLDER_DEFAULT_ALLOW=False` and verifying all allow rules are in place before upgrading.
- The `can_access_folder()` function evaluates deny rules first (deny wins), then allow rules, then default. This allows "allow everything except this subfolder" patterns.
- Admin UI's Permission Simulator shows "Default allow" in the matched rule column when no scope matches, helping admins understand which files are accessible by default.

## 5. Reusing `usage_logs` for Search History

**Status**: Implemented

**Context**: v0.4 needed to show users their recent searches and recently opened files. The database already had an `usage_logs` table that records every search (`action='search'`) and preview open (`action='open_preview'`). The question was whether to build on this existing table or create a new, dedicated history system.

**Decision**: **Reuse `usage_logs`** for audit/search history queries. Add only the `recent_files` table (new, lightweight) for the UI recents panel, capped at 50 rows per user.

**Rationale**:
- `usage_logs` already has `user_id`, `action`, `details_json` (stores search codes), and `created_at`. Querying recent searches is a simple `SELECT ... WHERE user_id=? AND action='search' ORDER BY created_at DESC LIMIT 10`.
- The `recent_files` table is needed because usage_logs doesn't track file-level open frequency — it records individual preview opens but not aggregated counts. A dedicated table with `open_count` and `last_opened_at` is cleaner than aggregating usage_logs on every request.
- Capping at 50 rows per user prevents unbounded growth. The primary key `(user_id, file_id)` means repeated opens update the same row (incrementing `open_count`, updating `last_opened_at`).
- Per-deploy TTL (`QUICKPEEK_HISTORY_RETENTION_DAYS`) cleans both tables — no per-user config needed.

**Alternatives Considered**

| Alternative | Why Rejected |
|-------------|--------------|
| Separate `search_history` table | Duplicates data already in `usage_logs`. Would need to write to two tables on every search. |
| Store recents in local storage (frontend only) | Wouldn't persist across devices or browsers. No server-side search history. |
| Single `recent_activity` table with polymorphic rows | More complex queries. The `action` column in `usage_logs` already serves this purpose. |
| No history (v0.3 behavior) | Rejected — search history is a core quality-of-life feature for v0.4. |

**Consequences**
- `GET /api/me/recent-searches` queries `usage_logs` directly — no new table for search history.
- `recent_files` is updated via the existing `/api/usage/open` endpoint — minimal code change.
- Per-deploy TTL means all users share the same retention policy. Per-user TTL is deferred to v0.5.
- History cleanup runs on every boot — for very large `usage_logs` tables, a startup spike in DELETE queries may cause brief slowness.

## 6. Admin-Only API Key Creation

**Status**: Implemented

**Context**: The API key system needed a creation model. Two approaches: admins create keys for anyone (top-down), or users self-serve keys with scoped permissions (bottom-up). Self-service introduces risk of permission escalation bugs and requires a permissions-aware UI for non-admin users.

**Decision**: **Admin-only** API key creation in v0.4. Only users with `manage_users` permission can create, list, and revoke keys.

**Rationale**:
- Admin-only creation prevents lateral movement — a compromised user account cannot create API keys to establish persistence.
- The permission intersection logic (`_build_api_key_user()` intersects key scopes with issuing user's permissions) is simpler to reason about with a limited set of creators.
- Self-service key generation requires a dedicated UI for users to create keys with a subset of their own permissions, plus permission intersection validation — significant UX and security design work that can be deferred.
- Admins have full visibility: the API Keys tab shows all keys, their scopes, last-used timestamps, and revocation status.

**Alternatives Considered**

| Alternative | Why Rejected |
|-------------|--------------|
| Self-service (users create their own keys) | Scope-confined key creation UI is complex. Risk of escalation bugs if intersection logic has edge cases. Deferred to v0.5. |
| Anyone can create keys for themselves | No accountability. A compromised low-privilege account could create unlimited keys. |
| API-only creation (no UI) | Admin UI is essential for discoverability and management. |
| Pre-seeded keys in config file | Inflexible — adding/revoking keys would require server restart. |

**Consequences**
- Creating an API key requires admin privileges — non-admin users who want automation must ask their IT admin.
- The "key created" modal forces the admin to copy the key before dismissing (Close button disabled until Copy is clicked), reducing support tickets from lost keys.
- The `api_keys` table has `revoked_at` for soft-revocation — no cascading deletes needed.

## 7. Per-Deploy History TTL (Not Per-User)

**Status**: Implemented

**Context**: Search history and recent files accumulate over time. A retention policy is needed to prevent unbounded database growth. Two approaches: a single global TTL applied to all users, or per-user TTL settings where each user controls their own retention.

**Decision**: **Per-deploy TTL** via `QUICKPEEK_HISTORY_RETENTION_DAYS` env var (default 90). Single setting for all users.

**Rationale**:
- A single env var is trivially simple to implement and configure — one line in config.py, one SQL DELETE per table in init_db().
- Per-user TTL would require a new user settings page (frontend), per-user configuration storage (new DB table or column), and additional query complexity — none of which justifies the benefit for v0.4.
- Users can clear their own history at any time via the "Clear" button in the recents panel (`DELETE /api/me/history`), giving them individual control without a per-user TTL setting.
- For enterprise deployments, IT admin control over retention is more important than user choice — compliance requirements often mandate data retention limits.

**Alternatives Considered**

| Alternative | Why Rejected |
|-------------|--------------|
| Per-user TTL in user settings | Requires user settings page, new DB table, frontend form, and backend endpoint. High complexity for v0.4. |
| No cleanup (retain forever) | Unbounded growth of `usage_logs` and `recent_files`. Could reach millions of rows in active deployments. |
| File-count based cleanup (keep last N entries per user) | Works but less predictable for admins — no clear way to calculate storage impact. |
| LRU eviction (keep most recent N entries) | Same problem — unpredictable from admin perspective. |

**Consequences**
- All users share the same retention window. A user who wants longer history than the deploy-level setting cannot override it (v0.5 feature).
- Cleanup runs on every boot — for deployments that restart frequently, cleanup queries run repeatedly but are cheap (indexed `WHERE created_at < datetime(...)`).
- `QUICKPEEK_HISTORY_RETENTION_DAYS=0` disables cleanup entirely — documented for deployments that want manual control.

## 8. Polyglot Auth Dispatch (JWT → API Key → 401)

**Status**: Implemented

**Context**: v0.4 added two new authentication methods (API key header and LDAP bind) to the existing JWT Bearer auth. The `current_user` dependency needed to support all three without breaking existing clients. The key design question was how to compose these: separate endpoints per auth method, a dispatch chain, or a unified authentication service.

**Decision**: A **single `current_user` dependency** that tries all three auth methods in a fixed order: Bearer JWT → `X-API-Key` header → 401. The token prefix (`qpk_`) distinguishes API keys from JWTs.

**Rationale**:
- Single dependency means every endpoint automatically supports all auth methods — no endpoint needs to know which method authenticated the request.
- The dispatch order (JWT → API key) means session tokens take priority, which matches user expectations: you're "logged in" as your user, not as your API key.
- The `qpk_` prefix provides a cheap heuristic to skip JWT decode for API keys — no need to try JWT decode on keys that obviously aren't JWTs.
- LDAP integration happens at the login endpoint (`POST /api/auth/login`), not in `current_user` — the login produces a standard JWT, so the dispatch chain remains unchanged.
- The fallback-to-401 pattern is standard FastAPI — `current_user` is a `Depends()` that either returns a user dict or raises `HTTPException(401)`.

**Alternatives Considered**

| Alternative | Why Rejected |
|-------------|--------------|
| Separate endpoints (`POST /api/auth/api-key-login`) | Creates a JWT for key-based auth, adds token expiry — defeats the purpose of long-lived keys. |
| Separate `Depends` functions (`Depends(current_user)` + `Depends(require_api_key)`) | Every endpoint needs to know which auth method to use. Breaks the single-dependency pattern. |
| Middleware-based auth (set request.user before route) | Works but hides auth logic from the dependency graph. OpenAPI docs lose auth method visibility. |
| gRPC-style interceptor | Overkill for FastAPI. Would require custom middleware not in the framework's standard patterns. |

**Consequences**
- API key users appear as "synthetic users" with negative IDs (`user["id"] = -api_key["id"]`) — code that checks user IDs must account for this or use `user.get("auth_source")`.
- The `current_user` function now has a polyglot structure that could grow complex if more auth methods are added (v0.5 may add bearer tokens from OIDC). A future refactoring into an `AuthService` class may be warranted.
- LDAP login and API key auth share the `current_user` dependency path — LDAP users get real user rows in the DB (with `auth_source='ldap'`), while API key users get synthetic, ephemeral dicts that never touch the users table.
